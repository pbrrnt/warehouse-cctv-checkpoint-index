2. รูปแบบป้ายทะเบียนไทย

2.1 โครงสร้าง 2 บรรทัด

┌─────────────────────────┐
│      1กก  1234          │  ← บรรทัดบน: หมวดอักษร + เลขทะเบียน
│    กรุงเทพมหานคร         │  ← บรรทัดล่าง: จังหวัด
└─────────────────────────┘

2.2 รูปแบบบรรทัดบน

รูปแบบ ตัวอย่าง หมายเหตุ
[เลข 1][พยัญชนะ 2] [เลข 1–4] 1กก 1234 รูปแบบปัจจุบัน (พบมากที่สุด)
[พยัญชนะ 2] [เลข 1–4] กท 5678 รูปแบบเดิม ยังพบได้มาก
[พยัญชนะ 1] [เลข 1–4] ก 1234 พบน้อย
[เลข 1][พยัญชนะ 1] [เลข 1–4] 1ก 234 พบน้อย

Regex สำหรับตรวจรูปแบบ (หลัง normalize แล้ว ตัดช่องว่างออก)

^([0-9]?)([ก-ฮ]{1,3})([0-9]{1,4})$
  • กลุ่ม 1 = เลขนำหน้า (อาจไม่มี)
  • กลุ่ม 2 = หมวดอักษร 1–3 ตัว (ปกติ 1–2)
  • กลุ่ม 3 = เลขทะเบียน 1–4 หลัก

2.3 ป้ายมอเตอร์ไซค์

  • มีเฉพาะด้านหลัง ไม่มีป้ายหน้า → ดูผลกระทบต่อการวางกล้องใน 10-chokepoint-design.md หัวข้อ 3.1
  • ขนาดเล็กกว่ารถยนต์มาก (~17.5 × 22 ซม. เทียบกับ 34 × 16 ซม.)
  • ตัวอักษรสูง ~5 ซม. เทียบกับรถยนต์ ~7 ซม. → เป็นตัวกำหนดเกณฑ์ FOV ของทั้งระบบ
  • บางรุ่นจัดวาง 3 บรรทัด (หมวด / เลข / จังหวัด) ต้องรองรับด้วย

2.4 สีป้ายบอกประเภทรถ

สีพื้น / สีอักษร ประเภท
ขาว / ดำ รถยนต์นั่งส่วนบุคคลไม่เกิน 7 คน
ขาว / น้ำเงิน รถยนต์นั่งส่วนบุคคลเกิน 7 คน (รถตู้)
ขาว / เขียว รถยนต์บรรทุกส่วนบุคคล (กระบะ)
เหลือง / ดำ รถรับจ้าง (แท็กซี่, สามล้อ)
เขียว / ขาว รถบริการธุรกิจ/ทัศนาจร
แดง / ดำ ป้ายแดง (ยังไม่จดทะเบียน)
ฟ้า / ขาว รถสถานทูต/องค์การระหว่างประเทศ

ยืนยันกับข้อมูลกรมการขนส่งทางบกก่อนนำไปใช้เป็นเกณฑ์ตัดสิน — ตารางนี้ใช้เป็น attribute เสริมเพื่อช่วยกรองผลค้นหา ไม่ใช่ข้อมูลทางกฎหมาย

การแยกสีป้ายต้องใช้ภาพจากกล้อง overview (ภาพสี) ไม่ใช่กล้อง lpr ที่เปิด IR แล้วได้ภาพขาวดำ

3. ชุดอักขระ

3.1 พยัญชนะไทยที่ใช้บนป้าย

พยัญชนะไทยมี 44 ตัว แต่ ฃ (ขวด) และ ฅ (คน) เป็นอักษรเลิกใช้ ไม่ปรากฏบนป้าย

ก ข ค ฆ ง จ ฉ ช ซ ฌ ญ ฎ ฏ ฐ ฑ ฒ ณ ด ต ถ ท ธ น
บ ป ผ ฝ พ ฟ ภ ม ย ร ล ว ศ ษ ส ห ฬ อ ฮ

ตรวจสอบกับข้อมูลจริงที่เก็บได้ในเฟส 2 แล้วตัดตัวที่ไม่เคยพบออกจาก charset เพื่อลดโอกาส OCR อ่านผิด

3.2 ตัวเลข

ป้ายไทยใช้ เลขอารบิก เป็นหลัก แต่ OCR อาจตีความเป็นเลขไทยได้ จึงต้องแปลงทุกครั้ง:

๐→0  ๑→1  ๒→2  ๓→3  ๔→4  ๕→5  ๖→6  ๗→7  ๘→8  ๙→9

5. อัลกอริทึม plate_normalize.py

5.1 ขั้นตอน

input: raw_text จาก OCR (2 บรรทัด), char_confs

1. ทำความสะอาด
   • ตัดช่องว่าง ขีด จุด และอักขระที่ไม่ใช่ [ก-ฮ0-9]
   • แปลงเลขไทย ๐-๙ → 0-9
   • แปลงอักษรละตินที่ปนมาเป็นเลข (O→0, I→1, ...)

2. แยกบรรทัด
   • บรรทัดที่มีตัวเลข = บรรทัดหมวด+เลขทะเบียน
   • บรรทัดที่มีแต่พยัญชนะและสระ = ชื่อจังหวัด

3. ตรวจเทมเพลตบรรทัดบน ด้วย regex ในหัวข้อ 2.2
   ├─ เข้ารูปแบบ  → ไปข้อ 5
   └─ ไม่เข้ารูปแบบ → ไปข้อ 4

4. แก้ด้วยตารางสับสน (repair)
   • ลองสลับตัวที่สับสนได้ทีละตัว (จำกัดไม่เกิน 2 ตัว เพื่อไม่ให้ระเบิด)
   • ให้คะแนนแต่ละความเป็นไปได้ = (เข้าเทมเพลตไหม) × (ค่า confidence เดิม) ÷ (ค่าปรับการสลับ)
   • เลือกตัวที่คะแนนสูงสุด ถ้าไม่มีตัวไหนเข้าเทมเพลตเลย เก็บของเดิมแล้วตั้ง flag

5. จับคู่จังหวัด
   • เทียบบรรทัดล่างกับ gazetteer 77 รายการ ด้วย Levenshtein
   • ถ้าระยะห่าง ≤ 3 → รับเป็นจังหวัดนั้น
   • ถ้าเกิน → เก็บเป็น NULL แต่ยังใช้ผลบรรทัดบนได้

6. คืนค่า
   • plate_norm  = "1กก1234"        (ไม่มีช่องว่าง สำหรับใช้ค้นหา)
   • raw_text    = ข้อความดิบจาก OCR (ห้ามทิ้ง)
   • province    = "กรุงเทพมหานคร" หรือ NULL
   • ocr_conf    = ค่าความมั่นใจรวม
   • char_confs  = ความมั่นใจรายตัวอักษร (JSONB)
   • flags       = ["template_mismatch"] ถ้ามี

5.2 ★ ห้ามทิ้ง raw_text

เก็บข้อความดิบจาก OCR ไว้เสมอ เพราะ:

  • ใช้ debug ว่าอ่านผิดตรงไหน
  • ใช้สร้าง confusion matrix จริงในเฟส 3
  • ถ้าอัลกอริทึม normalize มีบั๊ก ยังกู้ข้อมูลเดิมได้โดยไม่ต้องประมวลผลภาพใหม่

5.3 Majority vote ต่อ track

รถผ่านจุดคอขวดช้า ๆ จะได้หลายเฟรม → อย่าเชื่อเฟรมเดียว

สำหรับแต่ละ track:
  1. เก็บผล OCR ทุกเฟรมที่ได้ (ปกติ 3–15 เฟรม)
  2. โหวตทีละตำแหน่งตัวอักษร ถ่วงน้ำหนักด้วย char_conf ของเฟรมนั้น
  3. ประกอบผลลัพธ์แล้วตรวจเทมเพลตอีกครั้ง
  4. ocr_conf สุดท้าย = ค่าเฉลี่ยถ่วงน้ำหนัก × (สัดส่วนเฟรมที่เห็นตรงกัน)

การโหวตแบบนี้มักดันความแม่นขึ้นได้อีก 5–15 จุดเปอร์เซ็นต์ จากผลเฟรมเดียว

6. รายชื่อจังหวัด (Gazetteer)

77 รายการ = 76 จังหวัด + กรุงเทพมหานคร ใช้จับคู่บรรทัดล่างของป้าย

ภาคเหนือ (9)

เชียงราย เชียงใหม่ น่าน พะเยา แพร่ แม่ฮ่องสอน ลำปาง ลำพูน อุตรดิตถ์

ภาคตะวันออกเฉียงเหนือ (20)

กาฬสินธุ์ ขอนแก่น ชัยภูมิ นครพนม นครราชสีมา บึงกาฬ บุรีรัมย์ มหาสารคาม มุกดาหาร ยโสธร ร้อยเอ็ด เลย ศรีสะเกษ สกลนคร สุรินทร์ หนองคาย หนองบัวลำภู อำนาจเจริญ อุดรธานี อุบลราชธานี

ภาคกลาง (21) + กรุงเทพมหานคร

กรุงเทพมหานคร กำแพงเพชร ชัยนาท นครนายก นครปฐม นครสวรรค์ นนทบุรี ปทุมธานี พระนครศรีอยุธยา พิจิตร พิษณุโลก เพชรบูรณ์ ลพบุรี สมุทรปราการ สมุทรสงคราม สมุทรสาคร สระบุรี สิงห์บุรี สุโขทัย สุพรรณบุรี อ่างทอง อุทัยธานี

ภาคตะวันออก (7)

จันทบุรี ฉะเชิงเทรา ชลบุรี ตราด ปราจีนบุรี ระยอง สระแก้ว

ภาคตะวันตก (5)

กาญจนบุรี ตาก ประจวบคีรีขันธ์ เพชรบุรี ราชบุรี

ภาคใต้ (14)

กระบี่ ชุมพร ตรัง นครศรีธรรมราช นราธิวาส ปัตตานี พังงา พัทลุง ภูเก็ต ยะลา ระนอง สงขลา สตูล สุราษฎร์ธานี

6.1 กลุ่มจังหวัดที่จับคู่ผิดกันง่าย

ต้องระวังเป็นพิเศษเพราะชื่อคล้ายกัน:

กลุ่ม หมายเหตุ
นครปฐม / นครพนม / นครนายก / นครสวรรค์ / นครราชสีมา / นครศรีธรรมราช ขึ้นต้น "นคร" เหมือนกัน 6 จังหวัด
สมุทรปราการ / สมุทรสงคราม / สมุทรสาคร ขึ้นต้น "สมุทร" เหมือนกัน
ชัยนาท / ชัยภูมิ
สุรินทร์ / สุราษฎร์ธานี / สุพรรณบุรี / สุโขทัย
อุดรธานี / อุตรดิตถ์ / อุทัยธานี / อุบลราชธานี
ลำปาง / ลำพูน

→ ตอนจับคู่ ให้เทียบทั้งคำ ไม่ใช่แค่ 3–4 ตัวแรก และตั้งเกณฑ์ระยะห่างเข้มขึ้นสำหรับกลุ่มเหล่านี้

6.2 ★ ใช้จังหวัดช่วยยืนยันความถูกต้องรวม

ถ้าอ่านจังหวัดได้ชัด แต่บรรทัดบนไม่เข้าเทมเพลต → ควรเชื่อว่าเป็นป้ายจริงและพยายามซ่อมบรรทัดบนต่อ ถ้าอ่านจังหวัดไม่ได้เลยและบรรทัดบนก็ไม่เข้าเทมเพลต → น่าจะไม่ใช่ป้าย (อาจเป็นสติกเกอร์หรือข้อความอื่นบนรถ) ควรทิ้ง

7. การค้นหาแบบ Fuzzy

ผู้ใช้ต้องหาเจอแม้ระบบอ่านผิด 1–2 ตัว นี่คือเหตุผลที่การค้นหาต้องไม่เป็นแบบ exact match

7.1 กลยุทธ์สองชั้น

-- ชั้นที่ 1: กรองเร็วด้วย trigram index (GIN)
SELECT ... FROM plates
WHERE plate_norm % :query          -- ตัวดำเนินการ similarity ของ pg_trgm
ORDER BY similarity(plate_norm, :query) DESC
LIMIT 200;

-- ชั้นที่ 2: จัดอันดับใหม่ในแอป ด้วย weighted edit distance
--            ที่ใช้ตารางอักษรสับสนในหัวข้อ 4

เหตุผลที่แบ่งสองชั้น: pg_trgm เร็วมากเพราะมี index แต่ไม่รู้จักตารางอักษรสับสนของไทย ส่วน weighted edit distance แม่นกว่าแต่ช้าเกินกว่าจะรันทั้งตาราง → กรองหยาบด้วยชั้นแรก แล้วจัดอันดับละเอียดด้วยชั้นสอง

7.3 การแสดงผล

  • แสดง ค่าความมั่นใจ ทุกแถว เพื่อให้ผู้ใช้ตัดสินใจเองว่าจะไล่ดูอันไหนก่อน
  • แสดง ภาพ crop ของป้าย ข้างผลลัพธ์เสมอ — ให้ตามนุษย์ตัดสินขั้นสุดท้าย
  • ถ้ามี flag template_mismatch ให้ทำเครื่องหมายเตือน

8. โมเดลที่ใช้

ขั้นตอน โมเดล หมายเหตุ

OCR th_PP-OCRv5_mobile_rec (PaddleOCR) ความแม่นบนข้อความไทยทั่วไป ~82.7% — ต้อง fine-tune ด้วยภาพป้ายจริง
Runtime ONNX / OpenVINO บน iGPU Intel

8.1 แผนการ fine-tune (เฟส 3)

  1. ใช้ชุดภาพที่เก็บไว้ตอนตรวจรับงาน (samples/<SITE_ID>/) ติดป้ายกำกับด้วยมือ ~500–1,000 ป้าย
  2. รวมภาพจากหลายไซต์เพื่อให้โมเดลทนต่อสภาพที่ต่างกัน
  3. เน้นเก็บกรณีที่ยาก: กลางคืน มอเตอร์ไซค์ ป้ายสกปรก ป้ายเอียง
  4. วัดผลด้วย character-level accuracy ไม่ใช่แค่ exact match ทั้งป้าย (จะได้เห็นว่าดีขึ้นแค่ไหน)

9.2 ทดสอบ majority vote

  • ให้ผล OCR ปลอม 5 เฟรม ที่มี 3 เฟรมถูกและ 2 เฟรมผิดคนละแบบ → ผลโหวตต้องได้ค่าที่ถูก
  • ทุกเฟรมผิดเหมือนกันหมด → ต้องคืนค่าผิดนั้นพร้อม confidence ต่ำ (ไม่ใช่แกล้งบอกว่ามั่นใจ)

10. ความแม่นยำที่คาดหวังและวิธีวัด

สภาพ ความแม่นต่อเฟรม หลัง majority vote
มุมกล้องทั่วไป ไม่ควบคุมสภาพ 70–85% 80–90%
จุดคอขวดที่ออกแบบตามเอกสาร 10 88–93% ≥ 95%
กลางคืนไม่มีไฟเสริม 30–60% 50–70%
กลางคืนมี IR illuminator + shutter ล็อก 85–92% ≥ 93%

10.1 วิธีวัด

  1. ใช้ชุดภาพจาก samples/<SITE_ID>/ (~200 คัน รวมมอเตอร์ไซค์และรถกลางคืน)
  2. ติดป้ายกำกับด้วยมือ = ground truth
  3. วัด 2 ตัวเลข:
    • Exact match rate — ป้ายที่อ่านถูกทั้งใบ (ตัวเลขที่ผู้ใช้สนใจ)
    • Character accuracy — สัดส่วนตัวอักษรที่ถูก (ตัวเลขที่บอกว่าปรับปรุงได้แค่ไหน)
  4. แยกรายงานตาม: กลางวัน/กลางคืน, รถยนต์/มอเตอร์ไซค์

10.2 ★ ถ้าความแม่นต่ำกว่าเป้า ให้แก้ตามลำดับนี้

1. ตรวจคุณภาพภาพก่อน  →  ดู 10-chokepoint-design.md หัวข้อ 8
   (shutter, มุม, ขนาดตัวอักษร, แสง)
2. ปรับการเตรียมภาพ    →  warp, CLAHE, upscale
3. ปรับตารางอักษรสับสน →  ใช้ confusion matrix จริงจากข้อมูล
4. Fine-tune โมเดล OCR →  ขั้นสุดท้าย ใช้ต้นทุนสูงสุด

ห้ามข้ามไปข้อ 4 ก่อน — ในทางปฏิบัติ ปัญหาส่วนใหญ่แก้ได้ที่ข้อ 1 และการ fine-tune โมเดลบนภาพที่เบลออยู่แล้วจะไม่ช่วยอะไร
