1. ระบบนี้คืออะไร (และไม่ใช่อะไร)

ระบบนี้คือ ระบบนี้ไม่ใช่
ดัชนีสำหรับค้นหาว่า "ใคร/อะไร ผ่านประตูเมื่อไร" ระบบบันทึกวิดีโอ (NVR ทำหน้าที่นั้น)
เครื่องมือ จำกัดวงการค้นหา ให้เจ้าหน้าที่ หลักฐานเด็ดขาด — ต้องยืนยันด้วยวิดีโอจาก NVR เสมอ
ระบบที่ดูเฉพาะจุดคอขวดเข้า–ออก ระบบติดตามความเคลื่อนไหวทั่วทั้งโกดัง
ระบบแยกอิสระต่อโกดัง ระบบรวมศูนย์ (ยังไม่ทำ แต่ไม่ปิดทาง)

คำถามที่ระบบนี้ตอบได้:

  • "รถทะเบียน 1กก 1234 เข้ามาวันไหนบ้างในเดือนนี้"
  • "คนหน้าแบบนี้ (อัปโหลดรูป) เคยเข้ามากี่ครั้ง"
  • "รถกระบะสีขาวที่เข้าประตูใหญ่ช่วงบ่ายเมื่อวานมีคันไหนบ้าง"
  • "ตอนนี้มีรถอะไรอยู่ในโกดังบ้าง" (จากทิศทางเข้า–ออก)

คำถามที่ตอบไม่ได้: "คนนั้นเดินไปที่ไหนต่อหลังเข้ามา" — ต้องตามด้วย NVR เอง

3. ★ หลักการที่สำคัญที่สุด: Event-driven ไม่ใช่ Frame-driven

ปัญหา: เครื่องเป็น CPU-only การรันโมเดล AI หนัก ๆ ทุกเฟรมของทุกกล้องเป็นไปไม่ได้

วิธีแก้: แบ่งงานเป็นสองระดับที่มีต้นทุนต่างกันมาก

ระดับ ใคร ความถี่ โมเดล
ต่อเฟรม Frigate 5 fps × จำนวนกล้อง โมเดลเบา (detect วัตถุ) ทำงานเฉพาะเมื่อมี motion
ต่อเหตุการณ์ indexer ของเรา ~500 ครั้ง/วัน โมเดลหนัก (embedding, OCR) ทำครั้งเดียวต่อ tracked object 
รถ 1 คันวิ่งผ่าน  =  Frigate เห็น ~50 เฟรม  =  indexer ทำงาน 1 ครั้ง
                     (โมเดลเบา 50 ครั้ง)      (โมเดลหนัก 1 ครั้ง)

ผลลัพธ์: ต้นทุน AI ผูกกับ จำนวนเหตุการณ์ต่อวัน ไม่ใช่ จำนวนกล้อง × fps → ระบบทำงานได้บนมินิพีซี ฿8,000 และเพิ่มกล้องได้โดยต้นทุนโตช้ามาก

3.1 การเลือกเฟรมที่ดีที่สุด

indexer ไม่ได้ใช้เฟรมสุ่ม แต่ใช้ snapshot ที่ Frigate คัดมาแล้วว่าคะแนนสูงสุดของ track นั้น สำหรับใบหน้าเราคัดเพิ่มอีกชั้นด้วย blur score + ขนาดหน้า + มุมหน้า สำหรับป้ายทะเบียนเราใช้ หลายเฟรมแล้วโหวต เพราะ OCR ผิดพลาดง่ายกว่า (ดู 05-thai-lpr.md หัวข้อ 5.3)

4. ส่วนประกอบ

Service หน้าที่ Port
frigate RTSP ingest, decode, object detection, บันทึก 5000, 8554
mosquitto MQTT broker เชื่อม Frigate กับ indexer 1883
postgres metadata + vector (pgvector) 5432
redis คิวงานระหว่าง indexer worker (Redis Streams) 6379
indexer consume event → รันโมเดล → เขียน DB —
api FastAPI สำหรับค้นหา 8000
web หน้าเว็บภาษาไทย 8080

4.1 การไหลของข้อมูล

1. Frigate ตรวจพบวัตถุ → สร้าง tracked object
2. Frigate ส่ง MQTT: frigate/events {type: "end", after: {...}}
3. indexer รับ event → push เข้า Redis Stream
4. indexer worker ดึงงาน → เรียก Frigate API ขอ snapshot
       GET /api/events/<id>/snapshot.jpg
5. worker รันโมเดลตาม label:
       person          → face pipeline
       car/motorcycle  → vehicle + plate pipeline
6. worker เขียนผลลง Postgres + บันทึก crop ลง object store
7. worker ack งานใน Redis Stream

การรับมือความล้มเหลว: Redis Streams มี consumer group + ack ถ้า worker ตายกลางทาง งานจะถูกส่งให้ worker อื่นทำต่อ ไม่หายไปเฉย ๆ

5. เหตุผลของการเลือกเทคโนโลยี

ส่วน เลือก เหตุผลหลัก
RTSP/decode/record Frigate + go2rtc ปัญหา reconnect, codec เพี้ยน, timestamp drift, tiered retention ถูกแก้มาแล้ว (ADR-001)
Object detection OpenVINO บน Intel iGPU เป็น accelerator ที่มีอยู่แล้วในเครื่อง ไม่ต้องซื้อเพิ่ม
ฐานข้อมูล + vector PostgreSQL + pgvector metadata กับ vector อยู่ที่เดียว JOIN ตรง ๆ, ดูแล service น้อยลง 1 ตัว (ADR-007)
คิวงาน Redis Streams เบากว่า Kafka/RabbitMQ มาก แต่มี consumer group + ack ครบ
Object store filesystem + adapter local disk พอสำหรับไซต์เดียว สลับเป็น MinIO ได้เมื่อต้องรวมศูนย์
Face embedding ArcFace (InsightFace buffalo_l) มาตรฐานอุตสาหกรรม, ONNX รันบน OpenVINO ได้
Vehicle attrs / re-ID OpenVINO Model Zoo vehicle-attributes-recognition-barrier-0039, vehicle-reid-0001 — ออกแบบมาสำหรับ Intel โดยตรง
Thai OCR PaddleOCR th_PP-OCRv5_mobile_rec โมเดลไทยเดียวที่มีคุณภาพพอใช้เป็นฐาน fine-tune

6. ขอบเขตที่ชัดเจนระหว่างเรากับ Frigate

เราไม่แก้โค้ด Frigate สื่อสารผ่าน 2 ช่องทางเท่านั้น:

ช่องทาง ใช้ทำอะไร
MQTT frigate/events รับรู้ว่ามี tracked object ใหม่
MQTT frigate/tracked_object_update รับ metadata เพิ่มเติม
HTTP GET /api/events/<id>/snapshot.jpg ดึงภาพมาประมวลผล
HTTP GET /api/events/<id>/thumbnail.jpg ดึงภาพย่อสำหรับแสดงผล
HTTP GET /api/stats เฝ้าระวังสมรรถนะ

ประโยชน์: อัปเกรด Frigate ได้โดยไม่กระทบระบบเรา ตราบใดที่ API เหล่านี้ไม่เปลี่ยน

สิ่งที่ปิดใน Frigate (เพราะเราทำเอง — ดู ADR-002, ADR-003)

  • lpr — อ่านไทยไม่ได้
  • face_recognition — ไม่ให้ embedding ออกมา
  • semantic_search — ค้นได้แค่ระดับภาพรวมฉาก ไม่ใช่ re-ID และกิน RAM มาก

7. การออกแบบสำหรับหลายไซต์

แต่ละโกดัง = stack เดียวกันเป๊ะ ๆ ต่างกันแค่ไฟล์ .env

หลักการ ทำอย่างไร
มี site_id ตั้งแต่ schema แรก ทุกตารางหลักมีคอลัมน์นี้ แม้ตอนนี้ยังมีไซต์เดียว
ชื่อไม่ซ้ำข้ามไซต์ camera_id = <SITE_ID>-<จุด>-<บทบาท> เช่น WH01-GATE-LPR
ทุกไซต์รันเวอร์ชันเดียวกัน ปักหมุด image tag/digest และเวอร์ชันโมเดลใน .env
แก้ที่ต้นทางเสมอ ห้ามแก้โค้ดเฉพาะไซต์ — ถ้าต้องต่าง ให้ทำผ่าน config

ทางที่เปิดไว้แต่ยังไม่ทำ: ระบบรวมศูนย์ที่ยิงคิวรีไปทุกไซต์แล้วรวมผล — ทำได้ภายหลังโดยไม่แก้ระบบเดิม เพราะมี site_id และ API สม่ำเสมออยู่แล้ว

8. ข้อจำกัดที่ยอมรับไว้ตั้งแต่ต้น

ข้อจำกัด เหตุผลที่ยอมรับ
เห็นเฉพาะจุดคอขวด ไม่เห็นภายในโกดัง งานที่ยากคือหาเข็มในกองฟาง ส่วนการตามต่อในโกดัง NVR ทำได้อยู่แล้ว
ทางเข้า–ออกที่ไม่ได้ติดกล้อง = จุดบอด ต้องสำรวจให้ครบและ แจ้งผู้ใช้ให้รู้ตัว
ต้องพึ่ง NVR ในการดูวิดีโอเต็ม ประหยัดพื้นที่มหาศาลและไม่ทำงานซ้ำซ้อน
ความแม่นขึ้นกับงานติดตั้งหน้างาน เป็นเรื่องที่ควบคุมได้ ถ้าทำตาม 10-chokepoint-design.md
แต่ละไซต์ค้นได้เฉพาะข้อมูลของตัวเอง ตรงกับวิธีทำงานจริงที่เจ้าหน้าที่ค้นที่หน้างาน
