ADR-001 — ต่อยอด Frigate แทนเขียน pipeline วิดีโอเอง

วันที่: 2026-08-03 · สถานะ: ตัดสินใจแล้ว

บริบท: ต้องดึง RTSP จากกล้องหลายตัว decode ตรวจจับวัตถุ และบันทึกวิดีโอ

ทางเลือกที่พิจารณา

  1. เขียนเองทั้งหมดด้วย FFmpeg + OpenCV + YOLO
  2. ต่อยอด Frigate + go2rtc ← เลือก
  3. ใช้ go2rtc อย่างเดียวแล้วเขียน pipeline เอง

เหตุผล: ปัญหาที่กินเวลาจริงในระบบ RTSP คือ reconnect เมื่อกล้องหลุด, codec ที่กล้องจีนส่งมาไม่ตรงมาตรฐาน, timestamp drift, และการจัดการ retention — Frigate แก้ปัญหาเหล่านี้มาแล้วและมีคนใช้งานจริงจำนวนมาก การเขียนเองจะใช้เวลาหลายเดือนไปกับปัญหาที่ไม่ได้สร้างคุณค่าให้ผู้ใช้

ผลที่ตามมา: ต้องยอมรับข้อจำกัดของ Frigate และสื่อสารกับระบบผ่าน MQTT + HTTP API เท่านั้น ไม่แตะโค้ดภายใน

ผลที่ตามมา: เป็นงานเขียนเองที่หนักที่สุดในโปรเจกต์ ดู 05-thai-lpr.md

ADR-003 — ปิด face recognition ของ Frigate แล้วทำเอง

วันที่: 2026-08-03 · สถานะ: ตัดสินใจแล้ว

เหตุผล: face recognition ของ Frigate ให้ผลเป็น sub_label (ชื่อคน) แต่ ไม่ให้ embedding ออกมา ซึ่งเราต้องใช้ embedding เพื่อ:

  • ค้นย้อนหลังด้วยรูปภาพ ("อัปโหลดรูปนี้ แล้วหาว่าเคยมาวันไหน")
  • จัดกลุ่มใบหน้าที่ไม่รู้จัก (บุคคลนิรนาม) โดยไม่ต้องระบุชื่อล่วงหน้า

เมื่อจะทำ embedding เองอยู่แล้ว การเปิดของ Frigate ด้วยก็เป็นการเปลืองซีพียูซ้ำซ้อน

ADR-004 — วิเคราะห์เฉพาะจุดคอขวด ไม่สแกนทุกกล้อง

วันที่: 2026-08-04 · สถานะ: ตัดสินใจแล้ว · ผลกระทบสูงสุดในโปรเจกต์

บริบท: แต่ละโกดังมีกล้องได้ถึง 32 ตัว

เหตุผล: ความแม่นยำของ LPR และใบหน้าถูกกำหนดโดย สภาพภาพ (มุม ระยะ แสง ความเร็ว) มากกว่าคุณภาพโมเดล การสแกน 32 กล้องที่มุมทั่วไปจะได้ผลปานกลางทุกตัว (70–85%) แต่การวิเคราะห์ 2–4 กล้องที่ออกแบบเฉพาะจะได้ ≥95% และ ทุกคน/ทุกคันที่เข้าโกดังต้องผ่านประตูอยู่แล้ว

ผลที่ตามมา

  • ต้นทุนเครื่องลดจาก i7 32GB (~฿20,000) เหลือเครื่องระดับเริ่มต้น (~฿5,000–8,500 ดู 02-hardware-sizing.md) ต่อไซต์
  • มี compute เหลือให้ใช้โมเดลหนักขึ้น → คุณภาพขึ้นในขณะที่ต้นทุนลง
  • ขอบเขต PDPA แคบลงมาก อธิบายความได้สัดส่วนได้ง่ายกว่า
  • เพิ่ม dependency ใหม่: งานติดตั้งหน้างาน (กล้อง ไฟ ลูกระนาด) ซึ่งไม่ใช่งานซอฟต์แวร์
  • ยอมรับข้อจำกัด: ระบบรู้แค่ "เข้า–ออกเมื่อไร" ไม่รู้ว่าไปไหนต่อในโกดัง

ADR-005 — NVR เป็นตัวบันทึกหลัก ระบบเราเป็นดัชนีเสริม

วันที่: 2026-08-04 · สถานะ: ตัดสินใจแล้ว

เหตุผล: โกดังมี NVR ที่บันทึกวิดีโออยู่แล้วและใช้งานได้ดี ปัญหาที่แท้จริงคือ ค้นหาไม่ได้ ไม่ใช่บันทึกไม่ได้ การสร้างระบบบันทึกซ้ำเป็นการลงทุนที่ไม่จำเป็นและเพิ่มความเสี่ยง

ผลที่ตามมา

  • ระบบเราเก็บเฉพาะ snapshot, crop, embedding และคลิปสั้นเฉพาะเหตุการณ์ที่ประตู
  • พื้นที่จัดเก็บลดจากระดับ TB เหลือระดับร้อย GB
  • เกิดข้อบังคับใหม่: เวลาต้องตรงกับ NVR < 2 วินาที ไม่งั้นผลการค้นหาไร้ประโยชน์ (ดู ADR-006)

ADR-006 — บังคับซิงก์เวลา NTP ทั้งไซต์

วันที่: 2026-08-04 · สถานะ: ตัดสินใจแล้ว

ผลที่ตามมา: เพิ่มฟิลด์ clock_offset_ms ต่อกล้อง, สคริปต์ check_time_sync.py, และทำให้เป็นข้อตรวจรับงานทุกไซต์

ADR-012 — ตัดหน้าร้านออกจากขอบเขตโครงการ (เหลือ 3 โกดัง)

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว

บริบท: บริษัทมีพื้นที่ทั้งหมด 4 แห่ง — 3 โกดังที่มีจุดเข้า-ออกจุดเดียว และ 1 หน้าร้านกว้าง ~2 คูหา ที่รถวิ่งผ่านตลอดวันทั้งลูกค้าและไม่ใช่ลูกค้า

เหตุผล: หน้าร้านมีความถี่ของปัญหา (เช่น ลูกค้าแจ้งของขาด) ต่ำ และเมื่อเกิดปัญหาจริงยังใช้วิธีค้นจาก NVR ได้ตามปกติ (ช้ากว่าระบบนี้พอสมควรแต่ยอมรับได้เพราะเกิดไม่บ่อย) การลงทุนระบบสำหรับพื้นที่กว้างขนาดนี้ที่รถวิ่งผ่านหนาแน่นตลอดวัน ไม่ใช่แค่จุดเดียวแบบโกดัง ยังไม่คุ้มกับประโยชน์ที่เห็นในตอนนี้

ผลที่ตามมา

  • ขอบเขตโครงการเหลือ 3 โกดัง ไม่ใช่ 4
  • หน้าร้านอาจพิจารณาใหม่ในอนาคตถ้าเห็นประโยชน์ชัดเจนขึ้น — แต่ต้องออกแบบต่างจากรูปแบบจุดคอขวดที่ใช้กับโกดัง เพราะพื้นที่กว้างกว่าประตูเดียวมาก ไม่ใช่แค่ขยายจำนวนกล้อง

บริบท: ใน 3 โกดังที่อยู่ในขอบเขตโครงการ (หลัง ADR-012) — 2 แห่งยังใช้ XVR ของ Dahua อยู่ อีก 1 แห่งเป็น IP camera ล้วน

เหตุผล: โกดังนำร่องควรมีตัวแปรน้อยที่สุดเท่าที่ทำได้ เพื่อแยกปัญหาของระบบใหม่ออกจากปัญหาของโครงสร้างพื้นฐานเดิม ไซต์ XVR มีความไม่แน่นอนเพิ่มเติมที่ยังไม่เคยทดสอบ (การซิงก์เวลากับ XVR, การ map ช่องของกล้องที่อาจต่างจาก NVR ปกติ) ซึ่งควรแก้ทีหลังตอนมีประสบการณ์จากไซต์แรกแล้ว

ผลที่ตามมา

  • โกดังนำร่อง = ไซต์ที่เป็น IP camera ล้วน (ตัวเลือกเดียวที่เหลือหลังตัดหน้าร้านออก)
  • 2 ไซต์ XVR รอคิวไว้ก่อน — ยังไม่ปิดว่าต้องรอเปลี่ยนเป็น NVR เสมอไป Dahua XVR บางรุ่นเปิด RTSP ต่อช่องได้เหมือน NVR อยู่แล้ว ต้องทดสอบจริงตอนถึงคิว ไม่ใช่ด่วนสรุปว่าใช้ไม่ได้
  • ต้องเพิ่มขั้นตอนทดสอบเฉพาะ XVR ใน 03-camera-onboarding.md ก่อนขยายไปสองไซต์นี้ (ยังไม่ทำตอนนี้)

ADR-014 — ใช้ Tailscale เข้าถึงระบบทีละไซต์ แทนระบบรวมศูนย์

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว

บริบท: มี 3 ไซต์ในขอบเขตโครงการ ยังไม่ถึงจุดที่ต้องค้นข้ามไซต์บ่อยพอจะคุ้มกับการลงทุนระบบรวมศูนย์

เหตุผล: Tailscale ให้เข้าถึงหน้าเว็บค้นหาของแต่ละไซต์จากระยะไกลได้โดยไม่ต้องเปิดพอร์ตออกอินเทอร์เน็ต ตรงกับเงื่อนไข "ถ้าจำเป็นต้องเข้าจากภายนอก ให้ใช้ VPN เท่านั้น" ที่กำหนดไว้ใน 06-pdpa-compliance.md อยู่แล้ว ค่าใช้จ่ายและความซับซ้อนต่ำกว่าระบบรวมศูนย์มาก และไม่ปิดทางทำระบบรวมศูนย์ในอนาคต

ผลที่ตามมา

  • ★ ก่อนเปิดใช้งานจริง ต้องทำ 2 อย่างก่อน ซึ่งยังไม่มีทั้งคู่ (ยังไม่เขียนโค้ด): (1) เปิด built-in authentication ของ Frigate ไม่งั้นใครอยู่ใน tailnet เดียวกันก็เห็นภาพสด/คลิปได้หมด (2) มีระบบ login/RBAC ในชั้นแอป (web/api) เพราะ Tailscale ควบคุมแค่ว่า "เข้าเครือข่ายได้ไหม" ไม่ใช่ "มีสิทธิ์ดูข้อมูลอะไร"
  • ติดตั้งแบบไม่เปิด subnet routing เพื่อไม่ให้เห็นกล้อง/NVR ในวง LAN เดียวกันเกินขอบเขตที่ตั้งใจ
  • ถ้าไซต์ไหนไม่มีอินเทอร์เน็ตเลย จะใช้วิธีนี้ไม่ได้
  • รายการ "ระบบรวมศูนย์" ที่เคยค้างไว้ ปิดเป็น "ยังไม่ทำตอนนี้" — จะพิจารณาใหม่ก็ต่อเมื่อธุรกิจขยายจนคุ้มลงทุน

ADR-015 — ยืนยันทิศทางกล้อง LPR หันออกนอก + จุดติดตั้งบนเสาโครงสร้างประตู

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว

บริบท: จากภาพถ่ายหน้างานจริงของไซต์นำร่อง — "Entrance_1"/"Entrance_2" คือกล้องมุมกว้างที่มีอยู่แล้ว 2 ตัวถ่ายประตูเดียวกันจากมุมซ้ายและขวา ไม่ใช่คนละประตู ผู้ใช้ยืนยันให้กล้อง LPR หันออกนอกตามแผนเดิม (เห็นป้ายรถยนต์ด้านหน้า ไม่เห็นป้ายมอเตอร์ไซค์ตอนเข้า)

เหตุผล: เสาโครงสร้างสีแดงที่รับรางประตูบานเลื่อนอยู่ที่แนวประตูพอดี เป็นจุดติดตั้งที่ยึดกับอาคารจริง ไม่ใช่เสาลอยกลางแจ้ง แก้ปัญหาความเสี่ยงด้านความเสียหายที่กังวลไว้ได้โดยไม่ต้องขอเสาไฟฟ้า และไม่กระทบ logic ตรวจทิศทางเข้า/ออกของระบบ (อ้างอิงจากลำดับโซนที่ตัดผ่าน ไม่ใช่จากทิศทางกล้อง)

พบเพิ่มว่าประตูเดียวใช้ทั้งเข้าและออก — กล้องหันออกจะเห็น "หน้ารถ" ตอนเข้า และ "ท้ายรถ" ตอนออก มอเตอร์ไซค์ที่ไม่มีป้ายหน้าจึงยังถูกจับป้ายได้ตอนขาออก ไม่ได้พลาดทั้งหมดตามที่ ADR-009 กังวลไว้ในกรณีทั่วไป

ผลที่ตามมา

  • ติดตั้งกล้อง LPR บนเสาแดงที่แนวประตู สูง 1.0–1.5 ม. (คนละจุดกับกล้องมุมกว้างเดิมที่ติดสูงใกล้จั่วหลังคา)
  • ★ ต้องทดสอบ backlight เป็นพิเศษ — กล้องหันเข้าหาแสงกลางแจ้งขณะรถเป็นเงามืดในโกดัง เปิด WDR เต็มที่และทดสอบช่วงเที่ยงวันที่แสงจ้าที่สุดด้วย เพิ่มจากเช็กลิสต์เดิมที่ทดสอบแค่ 7:00/17:00
  • ADR-009 ยังใช้ได้ในกรณีทั่วไป (ไซต์ที่มีพื้นที่ถอยร่นพอ) — ไซต์นี้เป็นข้อยกเว้นที่มีทางแก้เฉพาะจากโครงสร้างอาคารที่มีอยู่ ไซต์อื่นต้องประเมินใหม่ตามหน้างานจริง

ADR-016 — วางแผนกล้อง LPR อาจต้องใช้ 2 ตัวตามพฤติกรรมจราจรจริง

วันที่: 2026-08-09 · สถานะ: ตัดสินใจบางส่วน — รอวัดหน้างานยืนยัน

บริบท: ประตูกว้างพอรับรถสิบล้อ/รถพ่วง จากการสังเกตจริง รถใหญ่ (สิบล้อ, รถพ่วง) เข้าทางขวาของภาพเพื่อถอยเข้าโซนจอดเฉพาะ ส่วนรถเล็ก (กระบะ, สี่ล้อ, หกล้อ) เข้าทางซ้ายกึ่งกลาง

เหตุผล: รถสองกลุ่มใช้เส้นทางต่างกันจริงภายในประตูเดียวกัน กล้องตัวเดียวที่ FOV แคบพอให้ตัวอักษรบนป้าย ≥25px (สูตรในหัวข้อ 3.3 ของ 10-chokepoint-design.md) อาจครอบคลุมไม่ถึงทั้งสองเส้นทางพร้อมกัน — รถใหญ่ที่ถอยเข้าช้า ๆ เป็นโอกาสจับภาพที่ดีเพราะแทบไม่เคลื่อนที่ ถ้าใช้กล้องแยกเฉพาะเลนนั้นน่าจะได้ความแม่นสูงมาก

ผลที่ตามมา

  • เผื่องบกล้อง LPR ตัวที่ 2 ไว้ในแผนจัดซื้อ (~฿4,000–8,000 เพิ่มเติม) แต่ยังไม่ฟันธงจนกว่าจะวัดระยะจริงหน้างานว่ากล้องเดียวครอบคลุมทั้งสองเลนได้ไหม
  • ปิดรายการค้างเดิมเรื่อง "1 หรือ 2 ตัว" บางส่วน — จากเดิมขึ้นกับ "เลนเข้า-ออกแยกกันไหม" เปลี่ยนเป็น "เลนรถใหญ่-รถเล็กแยกกันไหม" ซึ่งตอนนี้รู้แล้วว่าแยกจริง เหลือแค่วัดระยะเพื่อยืนยันจำนวนกล้อง

ADR-017 — ใช้ face recognition แบบ opt-in เท่านั้น (ปิดประเด็นฐานกฎหมาย)

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว

บริบท: คนเข้าพื้นที่ ~80% เป็นพนักงาน/ทีมงานเอง ~20% เป็นลูกค้า/บุคคลภายนอกที่เข้าไม่บ่อย — เข้าไม่บ่อยพอที่จะขอความยินยอมตรง ๆ ต่อหน้าได้จริงในทางปฏิบัติ (ต่างจากร้านหน้าถนนที่คนเดินผ่านตลอดเวลาซึ่งถูกตัดออกจากขอบเขตโครงการไปแล้วใน ADR-012)

ทางเลือกที่พิจารณา

  1. เก็บ embedding ของทุกคนที่ตรวจพบไว้ก่อน ใครไม่ยินยอมค่อยลบทีหลัง — ปฏิเสธ เพราะสลับด้านกับข้อกำหนด ม.26 ที่ต้องขอยินยอมก่อนเก็บ ไม่ใช่หลังเก็บ และในทางปฏิบัติระบบไม่มีทางรู้เองว่า embedding ไหนเป็นของคนที่ไม่ยินยอม ทำให้ "ลบทีหลัง" แทบเป็นไปไม่ได้จริง
  2. สร้าง face embedding เฉพาะคนที่อยู่ในรายชื่อที่ยินยอมแล้วเท่านั้น (opt-in watchlist) ← เลือก

เหตุผล: พนักงานเซ็นรับทราบตอนเข้างานได้ง่าย บุคคลภายนอกที่มาไม่บ่อยขอความยินยอมตรงหน้าได้จริงในทางปฏิบัติ

ผลที่ตามมา

  • วิดีโอยังบันทึกปกติสำหรับทุกคน (เหมือนกล้องวงจรปิดทั่วไป) — แค่ ไม่แปลงเป็น face embedding ที่ค้นหาได้ สำหรับคนที่ไม่อยู่ในรายชื่อยินยอม
  • ยกเลิกแผนเดิมเรื่อง "จัดกลุ่มใบหน้าคนแปลกหน้าอัตโนมัติ" แบบทำกับทุกคนที่ตรวจพบ — เปลี่ยนเป็นจับคู่กับรายชื่อที่ยินยอมแล้วเท่านั้น
  • ต้องมีขั้นตอนเก็บความยินยอม 2 แบบ: เอกสารพนักงาน (เข้างาน) และแบบฟอร์มสั้น ๆ สำหรับบุคคลภายนอกที่มาเป็นครั้งแรก
  • ป้าย PDPA ที่ทางเข้าต้องเพิ่มข้อความระบุการประมวลผลข้อมูลชีวมิติเมื่อเริ่มใช้ฟีเจอร์นี้จริง (ไม่ใช่แค่ "บันทึกภาพ" เฉย ๆ) — ร่างป้ายปัจจุบันใน 06-pdpa-compliance.md ยังเป็นเวอร์ชันที่ไม่มีใบหน้า ต้องอัปเดตก่อนเปิดใช้เฟส 4

ADR-018 — เลือกโมเดลใบหน้า YuNet + SFace แทน buffalo_l

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว

บริบท: ยืนยันว่ายังต้องการฟีเจอร์ค้นหาด้วยใบหน้า แม้คาดว่าจะใช้ไม่บ่อย

เหตุผล: buffalo_l (ArcFace) โค้ดเป็น MIT แต่ตัวโมเดลอนุญาตเฉพาะงานวิจัยไม่เชิงพาณิชย์ ต้องขอไลเซนส์แยกจาก InsightFace หากใช้เชิงพาณิชย์ — YuNet (ตรวจจับ) + SFace (embedding) จาก OpenCV Zoo เป็น Apache-2.0 ใช้เชิงพาณิชย์ได้ทันทีโดยไม่ต้องขอใคร

ผลที่ตามมา

  • ใช้ YuNet+SFace แทน buffalo_l ตั้งแต่เริ่มเขียน services/common/analytics/face.py ในเฟส 4
  • ต้องเผยแพร่ซอร์สโค้ดของระบบต่อสาธารณะ (เช่น ขึ้น GitHub) เพื่อให้ตรงเงื่อนไข AGPL-3.0 ของ YOLOv8 — ไม่มีค่าใช้จ่าย

ADR-019 — พารามิเตอร์ปฏิบัติการของไซต์นำร่อง (retention, Tier B, UPS)

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว

บริบท: ไซต์นำร่องมี Dahua NVR + กล้อง IP ~10–16 ตัวทั่วโกดัง (ยังไม่มีกล้อง LPR สักตัว) รวม 2 กล้องมุมกว้างที่มีอยู่แล้วคุมประตูเดียวกันจากมุมซ้าย-ขวา พื้นเป็นคอนกรีตเท (ไม่ใช่ดิน) แต่ฝนตกทำให้เป็นแอ่งน้ำขังบางจุด และมี UPS ที่ใช้กับ NVR อยู่แล้ว

การตัดสินใจ

  • Retention คลิปสั้น = 60 วัน (ปรับเพิ่มเป็น 90 วันได้ทีหลังเมื่อขยาย HDD โดยไม่ต้องแก้โค้ด) / snapshot-crop-metadata = 1 ปี เพราะกินพื้นที่น้อยมาก
  • กล้องมุมกว้างที่มีอยู่แล้ว (Tier B) ยังไม่เอาเข้าระบบดัชนี — ปล่อยเป็นกล้องเสริมนอกระบบไปก่อน รอผลใช้งานจริงจากจุดคอขวดก่อนตัดสินใจว่าคุ้มจะเชื่อมเข้าระบบไหม
  • แชร์ UPS เดิมของ NVR — สำรองไฟเกือบครึ่งชั่วโมง เพียงพอสำหรับ shutdown แบบมีระเบียบ
  • ควบคุมความเร็วรถของพนักงานตัวเองด้วยนโยบายภายในได้ (ไม่ต้องพึ่งลูกระนาดอย่างเดียว) — แต่คนขับรถภายนอก (รถส่งของ ฯลฯ) ไม่อยู่ในการควบคุมนี้ ลูกระนาดจริงยังจำเป็นสำหรับกลุ่มนั้น

ผลที่ตามมา

  • ต้องตั้งให้ Micro-PC shutdown อัตโนมัติเมื่อแบต UPS ใกล้หมด (เช่นผ่าน NUT — Network UPS Tools) ไม่งั้น Postgres เสี่ยงข้อมูลเสียหายจากไฟดับกะทันหัน — เพิ่มเป็นงานตั้งค่าเฟส 2
  • ยังไม่มีระบบ backup อัตโนมัติ (ไม่มีงบตอนนี้) — ยอมรับความเสี่ยงนี้ได้เพราะ NVR ยังเป็นแหล่งข้อมูลจริงเสมอ ถ้าดิสก์ระบบดัชนีพังคือ "ต้องสร้างดัชนีใหม่" ไม่ใช่ "หลักฐานหาย" — ทำ backup เพิ่มเมื่อมีงบ อาจทำพร้อมกับระบบ backup หลายไซต์ในอนาคต

ADR-020 — ใช้กล้องแบรนด์ Dahua เท่านั้น ไม่ใช้กล้องจีนทั่วไป

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว

บริบท: ระบบเดิมของบริษัทเคยมีกล้องจีนทั่วไปอยู่ แต่ถอดออกไปแล้วเพราะอัปเกรดเป็นกล้องแบรนด์ ปัจจุบันไซต์นำร่องเป็น Dahua ล้วนทั้ง NVR และกล้อง IP หลังอ่าน 03-camera-onboarding.md หัวข้อกับดักกล้องจีน (ไม่มี substream, UDP หลุดง่าย, fps ไม่ตรงสเปก, ต้องเดา RTSP URL เอง ฯลฯ) เห็นตรงกับปัญหาที่เคยเจอมาก่อนจนต้องถอดออก

เหตุผล: ประสบการณ์จริงยืนยันสิ่งที่เอกสารเตือนไว้แล้ว — กล้องจีนทั่วไปเพิ่มความเสี่ยงทางเทคนิคที่ไม่จำเป็น ในเมื่อ 2 ใน 3 โกดังที่เหลือในขอบเขตโครงการ (หลัง ADR-012) ก็เป็น Dahua อยู่แล้วทั้งคู่ (ผ่าน XVR) การซื้อกล้องใหม่ (LPR/overview/face) เป็น Dahua ทั้งหมดจึงตัดความไม่แน่นอนเรื่อง ONVIF/URL pattern/session limit ที่เอกสารเตือนไว้ออกไปเกือบทั้งหมด

ผลที่ตามมา

  • ซื้อกล้องใหม่ทุกตัว (LPR, overview, face) เป็น Dahua เท่านั้น — ใช้ URL pattern เดียว (rtsp://.../cam/realmonitor?channel=1&subtype=0|1) ทุกไซต์ ไม่ต้องเผื่อโค้ด ONVIF discovery สำหรับกล้องยี่ห้ออื่น
  • มีตัวเลือกเพิ่ม: Dahua มีกล้องซีรีส์ ANPR โดยเฉพาะ (ITC เช่น ITC413/ITC437) ที่ทำ shutter lock/WDR/vehicle capture ให้พร้อมในตัว ไม่ต้องตั้งเองตาม 10-chokepoint-design.md หัวข้อ 3.6 — แต่ราคาน่าจะสูงกว่ากล้อง IPC ทั่วไปที่ตั้งค่าเองพอสมควร ต้องเทียบราคาจริงก่อนตัดสินใจ ยังไม่ยืนยันว่าคุ้มกว่ากล้อง IPC ธรรมดา + ตั้งชัตเตอร์เอง
  • 03-camera-onboarding.md หัวข้อกล้องจีนทั่วไปยังเก็บไว้ในเอกสาร (เผื่ออนาคตมีไซต์ใหม่ที่ไม่ใช่ Dahua) แต่ไม่ใช่เส้นทางหลักของโปรเจกต์นี้อีกต่อไป
  • 2 ไซต์ XVR (ADR-013) มีโอกาสสูงขึ้นที่จะต่อได้ง่าย เพราะเป็น Dahua เหมือนกัน ไม่ใช่ยี่ห้ออื่นที่ไม่รู้พฤติกรรม

ADR-021 — ไม่ทำ plate_detect.py แยก ใช้ text detector ของ thai_ocr.py ตรง ๆ ก่อน

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว (ทดลอง — พร้อมกลับมาทบทวนถ้าจริงไม่พอ)

บริบท: ตามแผนเดิมใน 05-thai-lpr.md หัวข้อ pipeline plate_detect.py (YOLOv8n fine-tune หาตำแหน่งป้ายในภาพรถ) เป็นขั้นก่อน OCR — แต่ยังไม่มีโมเดล fine-tune กับป้ายไทยเลย ตัวเลือกที่มีคือ (1) ใช้ dataset ป้ายไทยบน Roboflow (พบจริง 3 แหล่ง เช่น thai-license-plate 153 รูป CC BY 4.0) มาเทรนเอง หรือ (2) ลองไม่มี detector แยกเลย

เหตุผล: ทบทวน 10-chokepoint-design.md แล้วพบว่ากล้อง role lpr ถูกออกแบบ FOV แคบ + ติดต่ำระดับป้าย + ระยะควบคุม (≤3.2 ม. ที่ 1080p) อยู่แล้วตั้งแต่ต้น — ภาพครอปวัตถุจากกล้องนี้จึงมีป้ายเป็นข้อความเด่นในเฟรมโดยธรรมชาติ ไม่ใช่ภาพรถทั้งคันมุมกว้างที่ต้องหาตำแหน่งป้ายก่อน ในเมื่อ thai_ocr.py มี text detector (PP-OCRv5_mobile_det) อยู่แล้วและทดสอบผ่านแล้ว การลองใช้ตรง ๆ ก่อนคือทางเลือกที่ต้นทุนต่ำสุด (ไม่ต้องเขียนโค้ดใหม่ ไม่ต้องหาโมเดลเพิ่ม) เทียบกับ dataset Roboflow ที่เล็กมาก (153-343 รูป) ไม่มีใครรายงาน mAP และโมเดล pretrained ที่มีอยู่เป็น cloud API (ขัดกับหลักการประมวลผล local ของทั้งโปรเจกต์)

ผลที่ตามมา

  • services/indexer/worker.py แยกตาม cameras.role: overview → วิเคราะห์รถ (vehicle.py), lpr → อ่านป้ายตรง (thai_ocr.py + plate_normalize.py) ไม่มีขั้น plate_detect คั่นกลาง
  • ยังไม่เคยทดสอบกับภาพจริงจากกล้อง (ดู docs/11-testing.md) — ความเสี่ยงคือ false positive จากข้อความอื่นในเฟรม (สติกเกอร์ ป้ายอื่น ๆ) ถ้าเกิดบ่อยตอนขึ้นระบบจริงค่อยกลับมาพิจารณา plate_detect.py แยกอีกที (มี dataset Roboflow ที่พบไว้แล้วเป็นจุดเริ่มถ้าต้องทำจริง)
  • 05-thai-lpr.md หัวข้อ pipeline/ตารางโมเดลต้องปรับให้ตรงกับการตัดสินใจนี้

ADR-022 — Search API เริ่มจากค้นหา+auth แบบง่ายก่อน ยังไม่ทำ RBAC เต็มรูปแบบ

วันที่: 2026-08-09 · สถานะ: ตัดสินใจแล้ว (เฟสเริ่มต้น — ทำ RBAC เต็มตอน face pipeline)

บริบท: docs/06-pdpa-compliance.md หัวข้อ 4 สเปก RBAC เต็มรูปแบบไว้แล้ว (บัญชีรายบุคคล, role viewer/investigator/manager/admin, audit log ทุกการเข้าถึง) แต่ตอนนี้ยังไม่มีระบบค้นใบหน้าเลย (ที่มาของความจำเป็นต้องคุม role investigator+ เข้ม) และยังไม่มีตาราง users ในระบบ

การตัดสินใจ: services/api/ เริ่มจาก endpoint ค้นหาหลัก 3 ตัว (/search/plates fuzzy สองชั้นตาม 04-data-model.md หัวข้อ 4.1, /search/vehicles ค้นแบบผสมหัวข้อ 4.4, /now รถที่ยังอยู่ในโกดังหัวข้อ 4.3) auth เป็น shared API key เดียว (header X-API-Key เทียบ API_SECRET_KEY) เทียบเท่า role viewer — ทุกคนที่มีคีย์เห็นข้อมูลเท่ากันหมด ยังไม่มี audit log — เพิ่มเข้ามาภายหลังในสโคปเดียวกัน: GET/PUT/DELETE /registry จัดการ plate_registry (ทะเบียนที่รู้จัก เช่น 'รถส่งของบริษัท ก', ธงเฝ้าระวัง) ใช้ auth เดียวกัน เพราะไม่ใช่ข้อมูลชีวมิติ (แค่ทะเบียน+ชื่อบริษัท) ความเสี่ยงต่ำกว่าการค้นใบหน้ามาก และผลค้นหา /search/plates จะแนบ owner_label/watch มาด้วยถ้าทะเบียนนั้นอยู่ใน registry (LEFT JOIN)

เหตุผล: RBAC เต็มรูปแบบมีไว้เพื่อกันสิทธิ์ค้นใบหน้าเป็นหลัก (ดู 06-pdpa-compliance.md: "การให้สิทธิ์ค้นใบหน้ากับทุกคนคือความเสี่ยงที่ไม่จำเป็น") ในเมื่อยังไม่มี face pipeline เลย การสร้างระบบ users+role+audit log เต็มรูปแบบตอนนี้คือสร้างของที่ยังไม่มีอะไรให้ป้องกันจริง เสียเวลาที่ควรเอาไปทำให้ค้นทะเบียน/รถใช้งานได้จริงก่อน (ตรงตามแนวทาง incremental ที่ใช้มาตลอดโปรเจกต์ — ดู ADR-008)

ผลที่ตามมา

  • ระบบเข้าถึงได้เฉพาะใน LAN ของโกดัง (ข้อกำหนดเดิมใน 06-pdpa-compliance.md หัวข้อ 4.1 ยังคงอยู่ — ห้ามเปิดออกอินเทอร์เน็ตโดยตรงไม่ว่า auth จะเป็นแบบไหน)
  • ก่อนเริ่ม face pipeline (เฟส 4) ต้องกลับมาทำ RBAC เต็มรูปแบบ ตามสเปกเดิมใน 06-pdpa-compliance.md — เพิ่มตาราง users, login endpoint, role-based route guard, ต่อ audit_log ที่มี schema อยู่แล้วในฐานข้อมูล (services/common/db/models.py) แต่ยังไม่มีโค้ดเขียนเข้า
  • shared key เดียวหมายความว่า ทุกคนที่ล็อกอินได้เห็นทุกอย่างเท่ากัน (ไม่มีการแยกสิทธิ์ค้นใบหน้าเพราะยังไม่มีใบหน้าให้ค้น) ต้องแจ้งผู้ใช้ระบบให้เข้าใจข้อจำกัดนี้ก่อนแจกคีย์ให้พนักงาน
  • services/api/*.py ยังไม่เคยรันกับ Postgres จริง (ดู docs/11-testing.md) — โดยเฉพาะ pg_trgm operator % และ DISTINCT ON ที่ query builder สร้างให้

ADR-023 — ตรวจสอบ config ก่อนขึ้นระบบจริงแบบ static (ไม่มี Docker ให้ทดสอบ)

วันที่: 2026-08-10 · สถานะ: เสร็จรอบแรกแล้ว — ทำซ้ำได้ทุกครั้งก่อนขึ้นระบบจริง

บริบท: ผู้ใช้ถามว่ามีอะไรทำได้อีกก่อนเครื่องจริงมา — เครื่องพัฒนาไม่มี Docker เลยตรวจแบบ static แทน (อ่านโค้ด/เอกสาร/config ไขว้กันหาจุดที่ขัดแย้งกัน, compile query เทียบ SQL, cross-check ตัวแปร .env กับ docker-compose.yml) แทนการรันจริง เจอบั๊กจริงหลายจุดที่จะทำให้ระบบไม่ทำงานหรือมีช่องโหว่ตั้งแต่วันแรกถ้าไม่แก้ก่อน

บั๊กที่เจอและแก้แล้ว

จุด ปัญหา ผลถ้าไม่แก้ แก้ที่ไหน
docs/09-multi-site-runbook.md ขั้นที่ 5.3 คำสั่ง docker compose up -d ไม่มี --profile app indexer/api/web ไม่สตาร์ตเลย มีแค่ infra แก้ลำดับขั้นตอนในรันบุ๊ก
เดียวกัน ไม่มีขั้นตอนรัน migration Postgres ว่างเปล่า ไม่มีตารางอะไรทั้งนั้น เพิ่มขั้นตอน alembic upgrade head
เดียวกัน ไม่มีขั้นตอนใส่ข้อมูล sites/cameras เงียบที่สุด — worker.py ข้าม event ทุกอันที่กล้องไม่รู้จัก ไม่มี error โผล่เลย ดูเหมือนระบบทำงานปกติทั้งที่ไม่มีข้อมูลเข้า DB เขียน scripts/seed_site.py ใหม่ + เพิ่มขั้นตอนในรันบุ๊ก
docker-compose.yml mosquitto port bind ${MQTT_PORT}:1883 ไม่มี 127.0.0.1: นำหน้า ต่างจาก postgres/redis — ขัดกับคอมเมนต์ใน mosquitto.conf เองที่บอกว่าตั้งใจให้เข้าถึงได้แค่ localhost (เพราะงั้นเลย allow_anonymous true) ใครก็ได้ในวง LAN ต่อ MQTT แบบไม่ต้อง auth ได้ เห็น/ปลอม frigate/events ได้ เติม 127.0.0.1:
frigate/config.yml hwaccel_args hardcode ค่าตรง ๆ แทนที่จะใช้ {FRIGATE_HWACCEL_PRESET} — ตัวแปรใน .env (FFMPEG_HWACCEL_PRESET) เดินทางผ่าน docker-compose.yml มาถึงแล้วแต่ไม่มีผลอะไรเลย เปลี่ยน .env ต่อไซต์ (CPU รุ่นต่างกัน) ไม่มีผล ขัดกับกฎ "ห้ามแก้โค้ดเฉพาะไซต์" ใน 09-multi-site-runbook.md ใช้ "{FRIGATE_HWACCEL_PRESET}" (ต้องมี quote เพราะ { นำหน้าค่าใน YAML ถ้าไม่ quote จะถูกตีความเป็น flow-mapping แล้ว parse error)
services/common/analytics/requirements.txt ใช้ opencv-python (ตัวเต็ม) ไม่ใช่ -headless import cv2 จะ ImportError: libGL.so.1... บน python:3.11-slim (ไม่มี libGL/libglib) ที่ services/indexer/Dockerfile ใช้ — เจอเฉพาะบน Linux container เท่านั้น เครื่องพัฒนา Windows ไม่เจอ เปลี่ยนเป็น opencv-python-headless

เหตุผลที่ทำแบบนี้ต่อ: ตรงกับที่ผู้ใช้ให้ความสำคัญไว้ (ดู memory feedback-observability-priority) — "บางปัญหาอาจจะไม่เจอตอนเทส" โดยเฉพาะบั๊กตัวสุดท้าย (opencv headless) ที่เป็นตัวอย่างชัดว่าทดสอบบนเครื่องพัฒนา (Windows) ผ่านหมดแต่จะพังบน target จริง (Linux container) — ต้องอาศัยการตรวจสอบ static/cross-reference แทนการรันจริง เพราะไม่มี Docker ให้ทดสอบ

ผลที่ตามมา

  • ควรทำ pass แบบนี้ซ้ำทุกครั้งที่แก้ docker-compose.yml/frigate config/Dockerfile ก่อนขึ้นระบบจริง ไม่ใช่แค่ครั้งเดียว
  • ยังมีความเสี่ยงแบบเดียวกัน (system library ที่ขาดใน Linux container) ที่ยังไม่ได้ตรวจละเอียดสำหรับ paddlepaddle/paddleocr — ยังไม่พบหลักฐานว่าเป็นปัญหา แต่ก็ยังไม่ได้ยืนยันว่าไม่ใช่ ต้องดู log ตอน docker compose build indexer ครั้งแรกจริง ๆ
  • รอบตรวจนี้ยังเจอว่า scripts/check_time_sync.py ที่ 08-nvr-integration.md หัวข้อ 7 และ 09-multi-site-runbook.md ขั้นที่ 6.2 อ้างถึงไม่มีไฟล์จริง (ทำเครื่องหมาย "จะเขียนในเฟส 2" ไว้ตั้งแต่แรก แต่ไม่เคยเขียน) — เขียนแล้ว (ONVIF GetSystemDateAndTime, ไม่ต้อง auth ตามสเปก) พร้อมโหมด --single <ip> ทดสอบทีละอุปกรณ์ตอนมีของจริง ยังไม่เคยทดสอบกับอุปกรณ์ ONVIF จริงเลย โครงสร้าง SOAP ตามสเปกมาตรฐานแต่กล้อง/NVR บางรุ่นอาจไม่ตรงเป๊ะ ต้อง verify ตอนมีเครื่องจริง — เพิ่มฟิลด์ ip เข้า site_config.example.json/seed_site.py schema ด้วย (คนละเรื่องกับ DB — cameras table ไม่มีคอลัมน์ ip เก็บไว้จริง)

  • กฎจับคู่แบบระวังไว้ก่อน (conservative 1:1): จับคู่เฉพาะเมื่อไม่กำกวมทั้งสองฝั่ง — ในกรอบเวลา window (default 3 วิ) รถคันนั้นมีป้ายเข้าเกณฑ์ใบเดียว และ ป้ายใบนั้นมีรถเข้าเกณฑ์คันเดียว ถ้ามีหลายตัว (รถตามกันมาติด ๆ) = ปล่อย NULL ไม่เดา
  • default = dry-run ต้อง --execute ถึงเขียนจริง

เหตุผล: สำหรับระบบช่วยค้นหา "ค้นเจอทะเบียนผิดคัน" แย่กว่า "ไม่มีทะเบียน" มาก — ทะเบียนผิดทำให้เจ้าหน้าที่ไปเปิด NVR ผิดจุด/สรุปผิดตัว ส่วนไม่มีทะเบียนก็แค่ใช้ตัวกรองอื่น (สี/ประเภท/เวลา) แทน กฎ 1:1 ยอมพลาดการจับคู่บางคู่ (recall ต่ำลง) เพื่อแลกกับความมั่นใจว่าคู่ที่จับได้ถูกจริง (precision สูง) — ตรงกับหลักการทั้งโปรเจกต์ (ดู ADR-021: ยอมพลาดดีกว่าเดาผิด)

ผลที่ตามมา

  • window 3 วินาที ยังไม่เคยพิสูจน์กับพฤติกรรมรถจริง — ระยะห่าง overview/lpr ขึ้นกับตำแหน่งกล้องจริงและความเร็วรถ ต้องวัดจากข้อมูลจริงหลังขึ้นระบบแล้วปรับ (สั้นไป = พลาดคู่ที่ควรจับ, ยาวไป = กำกวมบ่อยขึ้นจนจับไม่ได้เลย)
  • ไซต์ประตูเดียว (เช่นนำร่อง WH01: overview+lpr อย่างละตัว) ใช้ default (ไม่ส่ง camera_pairs) ได้เลย — ไซต์หลายประตูต้องส่ง camera_pairs ไม่งั้นรถประตู A อาจจับคู่ป้ายประตู B ที่บังเอิญเวลาใกล้กัน (โค้ดรองรับ param นี้แล้ว แต่ main() ยังไม่อ่านจาก config — ต้องต่อเมื่อมีไซต์หลายประตูจริง)
  • ยังไม่เคยรันกับ Postgres จริง — ต้องตั้ง cron รายวันหลังขึ้นระบบ (ดู 07-operations.md)

ADR-025 — HTTPS หน้าเว็บด้วย self-signed cert (nginx)

วันที่: 2026-09-02 · สถานะ: ตัดสินใจแล้ว

บริบท: 06-pdpa-compliance.md หัวข้อ 7 ระบุ "เข้ารหัสการรับส่ง — HTTPS สำหรับหน้าเว็บ (self-signed ในวง LAN ก็ได้)" หน้าเว็บเข้าถึง 2 ทาง: รปภ./เจ้าหน้าที่ในวง LAN (เข้าที่ IP เครื่อง) และเจ้าของรีโมตผ่าน Tailscale

ทางเลือกที่พิจารณา

  1. self-signed cert ใน nginx ← เลือก
  2. HTTP ใน LAN + พึ่ง Tailscale เข้ารหัสเฉพาะขารีโมต — ง่ายสุดแต่ในวง LAN เป็น plaintext ขัดกับ checklist HTTPS ในเอกสาร PDPA เอง
  3. Tailscale Serve (cert จริงจาก Let's Encrypt) — ไม่มี browser warning แต่ใช้ได้เฉพาะขา Tailscale ไม่ครอบคลุม LAN ในไซต์

เหตุผล: ตรงกับที่เอกสาร PDPA เขียนไว้พอดี ครอบคลุมทั้ง 2 ขา (LAN + Tailscale) ด้วย cert ใบเดียวที่ใส่ทั้ง IP และ Tailscale hostname เป็น SAN ไม่พึ่งอินเทอร์เน็ต/Let's Encrypt (บางไซต์อาจไม่มีเน็ต)

ผลที่ตามมา

  • scripts/gen_selfsigned_cert.sh สร้าง cert (SAN = LAN IP + Tailscale hostname, อายุ 10 ปี) ต้องรันบนเครื่องเป้าหมายก่อน docker compose --profile app up — cert mount ผ่าน volume ${DATA_ROOT}/certs ไม่ bake เข้า image (ความลับ + ต่างกันทุกไซต์)
  • web/nginx.conf: :80 redirect → :443, :443 เสิร์ฟด้วย cert; .env เพิ่ม WEB_PORT (https, default 8443) + WEB_HTTP_PORT (redirect, default 8080)
  • browser จะขึ้นคำเตือน "ไม่ปลอดภัย" ทุกครั้งที่เข้า (ปกติของ self-signed) — เจ้าหน้าที่ต้องกดผ่าน หรือติดตั้ง cert (web.crt) เป็น trusted ในเครื่องที่ใช้ประจำครั้งเดียว (แนะนำสำหรับ 2-3 เครื่องที่ใช้จริง) จดใน runbook แล้ว
  • ยังไม่เคยรันจริงกับ nginx/Docker (ไม่มี Docker บนเครื่องพัฒนา) — แต่ทดสอบ gen_selfsigned_cert.sh สร้าง cert จริงบนเครื่องพัฒนาแล้วว่า SAN/CN/อายุ ถูกต้อง (ผ่าน MSYS_NO_PATHCONV=1 เพราะ Git Bash บน Windows แปลง path /CN= ผิด — บน Linux ไม่มีปัญหานี้)

★ สิ่งที่ยังไม่ตัดสินใจ

รายการค้างทั้งหมดปิดแล้ว เหลือแค่การยืนยันหน้างานจริงตามที่ระบุไว้ใน ADR-016 (จำนวนกล้อง LPR 1 หรือ 2 ตัว) ก่อนสั่งซื้อของรอบสุดท้าย
