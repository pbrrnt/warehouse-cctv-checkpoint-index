1. ข้อมูลที่ระบบเก็บและระดับความอ่อนไหว

ข้อมูล ประเภทตาม PDPA ระดับความเสี่ยง
ภาพใบหน้า + face embedding ข้อมูลชีวมิติ = ข้อมูลอ่อนไหว (ม.26) สูงสุด
ป้ายทะเบียนรถ ข้อมูลส่วนบุคคล (ระบุตัวบุคคลได้ทางอ้อม) ปานกลาง
ภาพรถ สี ประเภท ข้อมูลส่วนบุคคลเมื่อเชื่อมกับทะเบียน ต่ำ–ปานกลาง
เวลาเข้า–ออก ข้อมูลส่วนบุคคลเมื่อเชื่อมกับบุคคล ปานกลาง
ภาพวิดีโอทั่วไป ข้อมูลส่วนบุคคล ต่ำ–ปานกลาง

1.1 ★ ทำไมใบหน้าถึงต่างจากป้ายทะเบียน

ข้อมูลชีวมิติเป็นข้อมูลอ่อนไหวตามมาตรา 26 ซึ่งมีข้อกำหนดเข้มกว่าข้อมูลส่วนบุคคลทั่วไปมาก โดยหลักต้องได้รับ ความยินยอมโดยชัดแจ้ง เว้นแต่เข้าข้อยกเว้นตามที่กฎหมายกำหนด

นี่คือเหตุผลที่แผนงานทำป้ายทะเบียนก่อนใบหน้า (ADR-008) — พิสูจน์คุณค่าของระบบด้วยส่วนที่ความเสี่ยงต่ำกว่าก่อน

2. ★ ข้อได้เปรียบของการทำเฉพาะจุดคอขวด

การเลือกวิเคราะห์เฉพาะประตูเข้า–ออก (ADR-004) ช่วยเรื่อง PDPA อย่างมาก:

หลักการตามกฎหมาย การทำเฉพาะจุดคอขวดช่วยอย่างไร
ความได้สัดส่วน (เก็บเท่าที่จำเป็น) เก็บเฉพาะจุดที่จำเป็นต่อวัตถุประสงค์ ไม่สแกนทั่วทั้งโกดัง
ความโปร่งใส ติดป้ายแจ้งได้ครบทุกจุดที่เก็บจริง เพราะมีแค่ 2–4 จุด
การจำกัดวัตถุประสงค์ ขอบเขตชัด: ควบคุมการเข้า–ออก ไม่ใช่เฝ้าดูพฤติกรรมพนักงาน
ลดปริมาณข้อมูล เก็บข้อมูลบุคคลน้อยลงมากเทียบกับการสแกน 32 กล้อง

ถ้าถูกตรวจสอบ การอธิบายว่า "เราสแกนเฉพาะประตู เพื่อควบคุมการเข้า-ออก และมีป้ายแจ้งทุกจุด" ทำได้ง่ายกว่าการอธิบายว่า "เราสแกนใบหน้าทุกคนทั่วทั้งโกดังตลอดเวลา" อย่างมาก

4. การควบคุมสิทธิ์ (RBAC)

หลักการ: การดูภาพกับการรู้ว่าเป็นใคร ต้องเป็นสิทธิ์คนละระดับ

บทบาท ค้นทะเบียน ดูภาพ/คลิป ค้นด้วยใบหน้า ดู/แก้ watchlist ตั้งค่าระบบ
viewer (รปภ.) ✓ ✓ ✗ ✗ ✗
investigator ✓ ✓ ✓ ดูอย่างเดียว ✗
manager ✓ ✓ ✓ ✓ ✗
admin ✓ ✓ ✓ ✓ ✓

เจ้าหน้าที่รักษาความปลอดภัยส่วนใหญ่ต้องการแค่ viewer — ค้นทะเบียนและดูภาพก็เพียงพอต่องานประจำวัน การให้สิทธิ์ค้นใบหน้ากับทุกคนคือความเสี่ยงที่ไม่จำเป็น

4.1 ข้อกำหนดเพิ่มเติม

  • บัญชีต้องเป็นรายบุคคล ห้ามใช้บัญชีร่วม (ไม่งั้น audit log ไร้ความหมาย)
  • บังคับเปลี่ยนรหัสผ่านเริ่มต้นตอนติดตั้ง
  • ระบบเข้าถึงได้เฉพาะใน LAN ห้ามเปิดออกอินเทอร์เน็ตโดยตรง
  • ถ้าจำเป็นต้องเข้าจากภายนอก ให้ใช้ VPN เท่านั้น

5. Audit Log

5.1 สิ่งที่ต้องบันทึก

การกระทำ บันทึกอะไร
เข้าสู่ระบบ / ออกจากระบบ ผู้ใช้, เวลา, IP
ค้นหาด้วยใบหน้า ผู้ใช้, เวลา, IP, ภาพที่ใช้ค้น (hash), จำนวนผลลัพธ์
ค้นหาด้วยทะเบียน ผู้ใช้, เวลา, คำค้น
ดูข้อมูลบุคคล ผู้ใช้, เวลา, person_id
เพิ่ม/แก้/ลบ watchlist ผู้ใช้, เวลา, ค่าก่อน-หลัง
ส่งออกรายงาน ผู้ใช้, เวลา, ขอบเขตข้อมูลที่ส่งออก
ลบข้อมูลตามคำขอ ผู้ใช้, เวลา, สิ่งที่ลบ

5.2 ข้อกำหนด

  • เก็บ audit log 3 ปี (นานกว่าข้อมูลที่ audit เอง)
  • ผู้ใช้ทั่วไปลบ audit log ไม่ได้ แม้แต่ admin
  • ทบทวน log เป็นระยะ — ดูว่ามีการค้นหาผิดปกติหรือไม่ (เช่น ค้นใบหน้าคนเดิมซ้ำ ๆ นอกเวลางาน)

6. Retention และการลบข้อมูล

6.1 นโยบายที่แนะนำ

ข้อมูล ระยะเวลา หมายเหตุ
คลิปวิดีโอ 90 วัน NVR มีของจริงอยู่แล้ว
snapshot / crop รถ 365 วัน
crop ใบหน้า ตามที่ฝ่ายกฎหมายกำหนด ★ ควรสั้นที่สุดเท่าที่ใช้งานได้
face_embeddings ตามที่ฝ่ายกฎหมายกำหนด ★ ข้อมูลชีวมิติ
ทะเบียน + metadata 365 วัน
audit_log 3 ปี

6.2 ข้อกำหนดทางเทคนิค

  • งานลบอัตโนมัติต้องรันทุกวัน และต้องลบไฟล์จริงใน object store ด้วย ไม่ใช่แค่ลบแถวใน DB
  • ต้องมีการตรวจว่าไม่มีไฟล์กำพร้าสะสม (ดู 07-operations.md)
  • การสำรองข้อมูลต้องมี retention ด้วย — ถ้า backup เก็บ 5 ปีแต่ข้อมูลจริงลบที่ 1 ปี ก็ยังถือว่าไม่ได้ลบ
  • บันทึกผลการลบลง audit log

6.3 ★ retention ของ backup

ถ้า face_embeddings เก็บ 180 วัน
→ backup ที่มี face_embeddings ต้องเก็บไม่เกิน 180 วันเช่นกัน
→ หรือแยก backup ที่ไม่มีข้อมูลใบหน้าออกมาต่างหากสำหรับเก็บยาว

จุดนี้มักถูกมองข้ามและทำให้ไม่ผ่านการตรวจสอบ

7. การรักษาความมั่นคงปลอดภัย

มาตรการ รายละเอียด
เข้ารหัสข้อมูลที่จัดเก็บ เข้ารหัสดิสก์ทั้งลูก (LUKS) บนเครื่องที่ไซต์
เข้ารหัสการรับส่ง HTTPS สำหรับหน้าเว็บ (self-signed ในวง LAN ก็ได้)
แยกเครือข่าย กล้องและ NVR อยู่ VLAN แยกจากเครือข่ายสำนักงาน
ไม่เปิดสู่อินเทอร์เน็ต ห้าม port forward เข้าระบบหรือกล้องโดยตรง
เปลี่ยนรหัสผ่านเริ่มต้น ทั้งกล้อง NVR และระบบ
อัปเดตความปลอดภัย ตั้งตารางอัปเดต OS และ Docker image
สำรองข้อมูลนอกไซต์ เข้ารหัสก่อนส่งออกนอกไซต์เสมอ

8. การใช้สิทธิของเจ้าของข้อมูล

ระบบต้องรองรับคำขอเหล่านี้ ภายในกรอบเวลาที่กฎหมายกำหนด

สิทธิ สิ่งที่ระบบต้องทำได้
ขอเข้าถึง ค้นและส่งออกข้อมูลทั้งหมดของบุคคลนั้น
ขอแก้ไข แก้ชื่อ/ข้อมูลใน persons
ขอลบ ลบ persons + face_embeddings + crop ใบหน้าที่เกี่ยวข้องทั้งหมด
ขอคัดค้าน หยุดประมวลผลข้อมูลของบุคคลนั้น (flag ไม่ให้เก็บ embedding ใหม่)

8.1 ข้อกำหนดของฟังก์ชันลบ

  • ลบทั้ง แถวใน DB และไฟล์ crop ในดิสก์
  • ลบใน backup ด้วย หรือมีกระบวนการรองรับที่บันทึกไว้
  • บันทึกการลบลง audit_log
  • ออกหลักฐานการลบให้ผู้ยื่นคำขอได้

ต้องทดสอบฟังก์ชันนี้จริงก่อนเปิดใช้งาน ไม่ใช่รอให้มีคำขอแรกแล้วค่อยพบว่าทำไม่ได้

9. ข้อควรระวังเฉพาะระบบนี้

ประเด็น คำแนะนำ
Face clustering สร้าง "บุคคลนิรนาม" แม้ไม่มีชื่อ ก็ยังเป็นข้อมูลชีวมิติที่ระบุตัวได้ ต้องอยู่ภายใต้กฎเดียวกันทุกประการ
watchlist ต้องมีเหตุผลรองรับ การใส่คนเข้า watchlist ต้องมีเหตุผลที่ชอบด้วยกฎหมายและบันทึกไว้ ไม่ใช่ใส่ตามใจ
อย่าใช้เฝ้าดูพฤติกรรมพนักงาน ระบบนี้มีวัตถุประสงค์ควบคุมการเข้า–ออก การเอาไปดูว่าใครมาสายเป็นการใช้ผิดวัตถุประสงค์
ป้ายทะเบียนเชื่อมโยงถึงบุคคลได้ อย่าคิดว่าทะเบียนไม่ใช่ข้อมูลส่วนบุคคล — เมื่อเชื่อมกับตัวตนแล้วก็เป็น
ผลลัพธ์ AI ไม่ใช่ข้อเท็จจริง ต้องมีคนตรวจสอบยืนยันด้วยวิดีโอเสมอ ห้ามใช้ผล AI ตัดสินลงโทษใครโดยตรง
แจ้งจุดบอดให้ผู้ใช้ทราบ อย่าให้เข้าใจผิดว่าระบบเห็นทุกคน อาจนำไปสู่ข้อสรุปที่ผิดพลาด
