1. เลือกเครื่อง

ระบบวิเคราะห์เฉพาะกล้องจุดคอขวด 2–4 ตัวต่อไซต์ (ดู 10-chokepoint-design.md) ภาระประมวลผลจึงต่ำกว่าที่คนส่วนใหญ่คาดมาก — งบเครื่องจึงควรน้อยที่สุดเท่าที่ยังผ่านเกณฑ์ แล้ว ย้ายส่วนต่างไปลงกล้อง LPR ซึ่งให้ผลตอบแทนต่อบาทสูงกว่ามาก

1.1 สี่ทางเลือก

ทาง ราคาโดยประมาณ idle power เหมาะกับ
Micro/Tiny มือสอง (ซีพียูรุ่นลงท้าย T) ฿5,000–6,500 ~15–18W งบจำกัด ต้องการประหยัดไฟ — แนะนำ
SFF/Tower มือสอง (ซีพียูปกติ) ฿4,000–5,000 ~20–25W งบต่ำสุด ไม่ติดเรื่องขนาดตัวเครื่อง
N100 / N305 กล่องจีนใหม่ ฿7,800–8,990 ~6–10W ไม่อยากยุ่งกับของมือสอง ประหยัดไฟสุด
Intel i3/i5 12–13th gen ใหม่, RAM 16–32GB ฿15,000–25,000 — เผื่อเพิ่มกล้องระดับ B ภายหลัง

ราคา N100 กล่องจีนในตลาดไทยจริงอยู่ที่ ~฿7,800–8,990 (ตัวเลข ฿7,000 ที่เคยระบุไว้ต่ำกว่าราคาตลาดจริง) แพงกว่า Micro/Tiny มือสองพอสมควร โดยได้เพิ่มมาแค่ idle power ที่ต่ำกว่า ~5–8W ซึ่งคิดเป็นค่าไฟต่างกันไม่ถึง ฿1,000 ตลอด 3 ปี — ไม่คุ้มกับส่วนต่างราคาที่เอาไปลงกล้อง LPR ได้มากกว่า

1.2 ข้อกำหนดขั้นต่ำที่ห้ามลดลง

รายการ ค่าขั้นต่ำ เหตุผล
CPU รองรับ AVX + AVX2 จำเป็น Frigate 0.17 บังคับใช้ และโมเดล ONNX/OpenVINO ต้องใช้
Intel iGPU (มี /dev/dri/renderD128) จำเป็น — Gen 6 ขึ้นไป decode วิดีโอด้วย VAAPI/QSV และรัน detector ผ่าน OpenVINO
RAM 8GB ขึ้นไป stack ทั้งหมดใช้ราว 6GB (Frigate + Postgres + Redis + indexer) — เพิ่มเป็น 16GB ตอนเข้าเฟส 4 (ใบหน้า)
ที่เก็บข้อมูลระบบ SSD (SATA หรือ NVMe) Postgres เขียนบ่อย — ห้ามลง OS/DB บน HDD
Ethernet Gigabit

1.3 ★★ กับดักตอนซื้อมือสอง: ซีพียูไม่มี AVX2

ซีพียูตระกูลประหยัดไฟราคาถูกหลายรุ่นที่เจอบ่อยตามร้านมือสอง ไม่มี AVX2 และ รัน Frigate 0.17 ไม่ได้เลย

★ ห้ามซื้อ สถาปัตยกรรม ปัญหา
Celeron J4125 / J4105 Gemini Lake ไม่มี AVX2
Celeron N5105 / N5095 Jasper Lake ไม่มี AVX2
Celeron J1900 / N3350 / N4000 รุ่นเก่ากว่า ไม่มี AVX2

ซีพียูกลุ่มนี้มักโผล่มาเป็นอันดับแรกเวลาค้นหา "mini pc ราคาถูก" เพราะราคาล่อใจมาก (~฿3,000–5,000) แต่ซื้อมาแล้วใช้กับระบบนี้ไม่ได้เลย ต้องเช็กรุ่นซีพียูให้ชัดก่อนโอนเงินทุกครั้ง

1.4 ★ วิธีได้เครื่องประหยัดไฟในงบจำกัด: มองหาเลข "T" ต่อท้าย

ซีพียู Intel สายธุรกิจ (OptiPlex / ThinkCentre / EliteDesk) มีสองเวอร์ชันสเปกเดียวกัน ต่างแค่ TDP:

รุ่น ตัวอย่าง TDP ใช้ในฟอร์มแฟกเตอร์
ปกติ i5-8400 65W SFF / Tower — ตัวใหญ่
ลงท้าย T i5-8500T 35W Micro / Tiny / Mini — ตัวเล็ก

วัดจริงจาก ServeTheHome: Dell OptiPlex Micro กับ i5-8500T กิน idle ~18W เทียบ SFF ตัวปกติ ~20–25W และตัวเรือนเล็กพอวางในตู้ควบคุมหน้าประตูได้

รุ่นที่ควรมองหา (มือสองในไทย)

ตระกูล รุ่น ซีพียูที่ต้องการ

คำค้นหาที่ใช้ได้ผล — ร้านมือสองไทยมักไม่เขียนคำว่า "Micro"/"Tiny" ตรง ๆ ลองค้น:

ดูได้ทั้ง Facebook Marketplace, กลุ่มคอมมือสอง, ร้านมือสองแถวบ้านหม้อ/พันทิปพลาซ่า — เป็นของเหลือจากองค์กรที่เปลี่ยนรอบเครื่อง เข้าตลาดมือสองสม่ำเสมอ

1.5 ★ เช็กลิสต์ก่อนซื้อมือสอง

1.6 กรณี HDD ติดเครื่องมาด้วย

ไม่ต้องทิ้ง — ใช้แยกหน้าที่กับ SSD ที่ซื้อเพิ่มตามหลักการในหัวข้อ 3.4:

SSD (ซื้อเพิ่ม)   →  OS + Postgres + crop     ← ต้องเร็ว
HDD (ติดมากับเครื่อง) →  คลิปวิดีโอ /data/media   ← เขียนเรียง ไม่ต้องเร็ว

1.7 ★ ควรใช้งบไปกับอะไร

งบต่อไซต์ ~฿27,000 (เครื่องมือสองประหยัดไฟ + SSD)

   เครื่องประมวลผล    ▓▓                          ~฿6,000   (22%)
   กล้อง LPR + ไฟ      ▓▓▓▓▓▓▓▓▓▓▓▓▓             ~฿15,000  (56%)
   งานติดตั้ง/โยธา     ▓▓▓▓▓▓                     ~฿6,000   (22%)

การประหยัดค่ากล้อง LPR ลง ฿3,000 แล้วทำให้ความแม่นตกจาก 95% เหลือ 75% ไม่คุ้ม เพราะทำให้ทั้งระบบเสียคุณค่า — ในขณะที่การเปลี่ยนเครื่องประมวลผลจากมือสองประหยัดงบเป็นรุ่นแพงกว่า แทบไม่ช่วยอะไรเลยเมื่อมีแค่ 3 กล้อง

2. คำนวณภาระประมวลผล

2.1 Frigate (ทำงานต่อเฟรม)

งาน ต้นทุน
decode substream 640×480 ~2–3% CPU ต่อกล้อง (ผ่าน iGPU)
motion detection ~1–2% CPU ต่อกล้อง
object detection (OpenVINO, ทำเฉพาะตอนมี motion) 10–20 ms ต่อครั้ง

สูตรประมาณ

inference ต่อวินาที = จำนวนกล้อง × detect_fps × สัดส่วนเวลาที่มี motion

ตัวอย่างที่ประตูโกดัง: 3 กล้อง × 5 fps × 20% (มีรถผ่านเป็นช่วง ๆ) = 3 inference/วินาที ความสามารถของเครื่องระดับเริ่มต้น (N100 หรือ Micro/Tiny มือสอง i5-T series) ≈ 50–100 inference/วินาที → เหลือหัวเยอะมาก

ตัวเลขในหัวข้อนี้อิงจาก N100 (4 E-core) เป็นกรณีระวังที่สุด — ถ้าใช้เครื่องมือสอง i5-*T (6 คอร์จริง) ตามหัวข้อ 1.4 จะเร็วกว่านี้พอสมควร

2.2 Indexer (ทำงานต่อเหตุการณ์ ไม่ใช่ต่อเฟรม)

งาน เวลาต่อครั้งบนเครื่องระดับเริ่มต้น (N100)
face detect + ArcFace embedding 40–60 ms
vehicle attributes + re-ID ~20 ms
plate detect + Thai OCR 150–300 ms
รวมต่อ 1 เหตุการณ์รถ ~200–350 ms

ปริมาณงานจริงที่โกดัง: สมมติรถเข้า-ออก 300 คัน/วัน + คนเดิน 200 คน/วัน → ~500 เหตุการณ์/วัน × 0.3 วินาที = ~2.5 นาทีของงาน AI ต่อวัน

นี่คือเหตุผลที่ event-driven ทำให้ CPU-only เป็นไปได้ — เครื่องว่างเกือบตลอดเวลา

2.3 ตัวชี้วัดที่ต้องเฝ้าดู

ดูที่ http://<ip>:5000/api/stats

ตัวชี้วัด เกณฑ์ ถ้าไม่ผ่านแปลว่า
inference_speed < 25 ms detector ช้าเกิน — ตรวจว่าใช้ iGPU จริงไหม
camera_fps ตรงกับที่ตั้ง กล้องส่งไม่ทัน หรือเครือข่ายมีปัญหา
skipped_fps = 0 เครื่องไม่ไหว — ต้องลด fps หรือเพิ่มเครื่อง
detection_fps ตามความหนาแน่นจริง ถ้าสูงผิดปกติ = motion mask ตั้งไม่ดี

3. พื้นที่จัดเก็บ

3.1 ต่อไซต์ (3 กล้องจุดคอขวด)

ข้อมูล สูตรคำนวณ ประมาณการ
คลิป HD เฉพาะเหตุการณ์ที่ประตู 300 เหตุการณ์/วัน × 20 วิ × 4 Mbps ≈ 3 GB/วัน ~270 GB ที่ 90 วัน
snapshot เต็มเฟรม 500/วัน × 300 KB ≈ 150 MB/วัน ~55 GB ที่ 1 ปี
crop (หน้า/รถ/ป้าย) 1,500/วัน × 40 KB ≈ 60 MB/วัน ~22 GB ที่ 1 ปี
Postgres (metadata) ~2 KB/เหตุการณ์ ~1 GB ที่ 1 ปี
embedding 512-d float32 = 2 KB + index ~5 GB ที่ 1 ปี
รวม ~350 GB → NVMe 1TB เพียงพอมาก

3.2 สูตรสำหรับคำนวณไซต์ของคุณเอง

พื้นที่ต่อวัน (GB) ≈
      (เหตุการณ์รถต่อวัน × ความยาวคลิป(วิ) × bitrate(Mbps) ÷ 8000)      ← คลิป
    + (เหตุการณ์ทั้งหมดต่อวัน × 0.3 MB ÷ 1000)                          ← snapshot
    + (เหตุการณ์ทั้งหมดต่อวัน × 3 × 0.04 MB ÷ 1000)                     ← crop
    + (เหตุการณ์ทั้งหมดต่อวัน × 0.01 MB ÷ 1000)                         ← DB + embedding

พื้นที่ที่ต้องมี = พื้นที่ต่อวัน × วันที่เก็บ × 1.3   (เผื่อ 30%)

ตัวอย่างโกดังที่รถเข้าออกหนาแน่น (1,000 คัน/วัน, เก็บ 180 วัน)

คลิป:     1000 × 20 × 4 ÷ 8000     = 10.0 GB/วัน
snapshot: 1500 × 0.3 ÷ 1000        =  0.45 GB/วัน
crop:     1500 × 3 × 0.04 ÷ 1000   =  0.18 GB/วัน
DB:                                ≈  0.02 GB/วัน
รวม ≈ 10.65 GB/วัน × 180 วัน × 1.3 = ~2.5 TB   → ต้องใช้ NVMe 4TB

3.3 ★ ปุ่มปรับที่ประหยัดพื้นที่ได้มากที่สุด

เรียงตามผลกระทบ:

  1. ลดวันเก็บคลิป HD (เก็บ 30 วันแทน 90) — ลดได้ ~65% เพราะคลิปกินพื้นที่ 80% ของทั้งหมด
  2. บันทึกคลิปเฉพาะ alert ไม่บันทึก detection — ตัดเหตุการณ์ที่ไม่สำคัญออก
  3. ลดความยาวคลิปเป็น 10 วินาที — แค่พอยืนยันว่าใช่เหตุการณ์ที่หา แล้วไปดูเต็มที่ NVR
  4. ไม่บันทึกคลิปเลย เก็บแค่ snapshot — เหลือ ~1 GB/วัน แต่ผู้ใช้ต้องไป NVR ทุกครั้ง

snapshot, crop และ embedding กินพื้นที่น้อยมาก จึงควรเก็บยาว (1 ปีขึ้นไป) ส่วนคลิปคือตัวที่ควรตัด เพราะ NVR มีของจริงอยู่แล้ว

3.4 การจัดพาร์ทิชัน

/            50 GB    ระบบปฏิบัติการ
/var/lib/docker   100 GB    image และ volume
/data/postgres    100 GB    ฐานข้อมูล (NVMe)
/data/media       ที่เหลือ  คลิป snapshot crop

ตั้ง alert เมื่อพื้นที่เหลือ < 15% (ดู 07-operations.md)

4. เครือข่าย

รายการ ประมาณการ
substream ต่อกล้อง (detect) ~1 Mbps
mainstream ต่อกล้อง (บันทึกเหตุการณ์) ~4 Mbps
รวม 3 กล้องจุดคอขวด ~15 Mbps

ไม่เป็นภาระต่อเครือข่ายโกดังทั่วไป แต่ต้องระวัง: NVR ก็ดึง mainstream จากกล้องเดียวกันอยู่แล้ว → กล้องต้องรองรับ RTSP session พร้อมกันได้อย่างน้อย 2 ตัว ทดสอบข้อนี้ตอนสำรวจ (ดู 03-camera-onboarding.md)

5. เมื่อไหร่ที่ต้องอัปเกรด

อาการ สาเหตุที่น่าจะเป็น ทางแก้ตามลำดับ
skipped_fps > 0 detector ไม่ทัน 1. ลด detect_fps เป็น 3 <br> 2. ปรับ motion mask ให้แคบลง <br> 3. เพิ่ม Coral TPU (~฿1,500) <br> 4. เปลี่ยนเครื่อง
indexer ทำงานไม่ทัน (Redis Stream ค้างสะสม) เหตุการณ์เยอะเกิน เพิ่มจำนวน worker ใน compose
ค้นหาช้า > 2 วินาที index ไม่ถูกใช้ หรือข้อมูลโตเกิน 1. ตรวจ EXPLAIN ANALYZE <br> 2. ปรับพารามิเตอร์ HNSW <br> 3. เพิ่ม RAM
พื้นที่เต็ม retention ยาวเกิน ดูหัวข้อ 3.3

ในทางปฏิบัติ ไซต์ที่มี 3 กล้องจุดคอขวดแทบไม่มีทางชนเพดานของเครื่องระดับเริ่มต้นเลย ไม่ว่าจะเป็น N100 หรือ Micro/Tiny มือสอง ถ้าชน ให้ตรวจการตั้งค่าก่อนสรุปว่าเครื่องไม่พอ — สาเหตุที่พบบ่อยที่สุดคือ motion mask ตั้งไม่ดีทำให้ detector ทำงานตลอดเวลาโดยไม่จำเป็น
